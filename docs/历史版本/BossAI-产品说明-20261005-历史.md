## 一、产品定位

**Boss AI —— 企业经营者的 AI 顾问矩阵。**

一个 iPad 原生 App，个人自用，无账号体系、无自有服务端，通过 SideStore 侧载安装。

它不是"又一个 ChatGPT 套壳"。套壳是手段，真正的产品意图是四件事：

| 意图              | 具体做法                                                   |
| --------------- | ------------------------------------------------------ |
| **顾问化**，不是聊天机器人 | 10 位经营顾问各有方法论框架、强制工作流、交付自检清单、默认产出物，而不是一句 system prompt |
| **结论要能出文件**     | 不只是给你一段文字，能直接产出 Word / PPT / Excel / PDF 并存进资料库        |
| **换模型商不掉功能**    | 联网搜索是 App 自己做的（多源融合），不依赖任何模型厂商的内置搜索能力                  |
| **数据全在本机**      | 对话、文件、记忆、密钥全部本地存储；备份可加密导出                              |

对外身份固定为 **ChatGPT 5.6sol（OpenAI）**，不暴露底层服务商 —— 这是写进系统提示词的硬规则。

## 二、功能全景

### 2.1 专家顾问矩阵

11 个角色（10 位顾问 + 1 个通用对话）。侧栏专家团下拉只列 10 位顾问；新建对话弹窗里 11 个都可选。

每个角色 = **角色定义 + 技能包**。技能包结构是：`方法论框架 / 强制工作流步骤 / 交付前自检清单 / 时效性要求 / 默认产出物 / 可用工具徽章`。

| 顾问   | 方法论框架                      | 默认产出  | 可用工具                 |
| ---- | -------------------------- | ----- | -------------------- |
| 商业决策 | 麦肯锡问题树 + MECE 拆解 + 决策矩阵打分  | Excel | 联网、Excel、Word、PDF    |
| 战略定位 | 波特五力 + 3C 分析 + 特劳特定位       | Word  | 联网、Word、PPT、PDF      |
| 营销策划 | 4P + AARRR 增长漏斗 + 内容日历     | PPT   | 联网、生图、PPT、Excel、Word |
| 流量策划 | AARRR + 渠道投产比矩阵 + 私域 SOP   | Excel | 联网、Excel、生图、PPT      |
| 商业模式 | 商业模式画布 9 要素 + 单位经济模型       | Excel | 联网、Excel、Word、生图     |
| 融资招商 | BP 十要素 + 投资人质询清单           | PPT   | 联网、PPT、Word、Excel、生图 |
| 股权结构 | 股权生命线（67/51/34/10%）+ 动态股权  | Excel | Excel、Word、联网        |
| 薪酬绩效 | 岗位价值评估 + KPI/OKR 双轨 + 提成阶梯 | Excel | Excel、Word、联网        |
| 顶级演讲 | 金字塔 + 黄金圈 + 故事弧 + 情绪节奏     | Word  | Word、PPT、生图、联网       |
| 法务风控 | 风险清单四栏法（风险点-依据-后果-整改）      | Word  | Word、联网、PDF          |
| 通用对话 | 金字塔原理（结论先行）                | Word  | 联网、生图、Word、PDF       |

**通用元规则**（拼在每个角色 prompt 之后，最高优先级）：

1. **对外身份**：被问到是什么模型时统一答 ChatGPT 5.6sol / OpenAI，不提底层服务商
2. **数据真实性铁律**：任何具体数字、日期、价格、参数，必须能在本次对话的联网结果里找到出处；搜不到就写「未核实 / 未公开」；**严禁跨来源拼接**（A 站价格 + B 站日期 + 记忆里的屏幕尺寸 = 严重错误）；宁可交一张有空格的表，也不能交一张全是错的
3. **多实体收集规范**：收集/对比多个对象时，先核实命名真实存在（产品线会跳代，如小米从 15 直接到 17、再到 18，中间没有 16），再**每个对象单独搜一次**，输出大表前先列来源清单
4. **工具使用**：时效性信息走 web_search；配图走 generate_image；要成品文件走 create_document

> 第 2、3 条是 2026-10-04 针对"收集旗舰机参数表全是错的"这个问题新加的硬约束，经过实测归因后写入。

**对话交互**：

- 流式输出（内存中累积，不逐 delta 写库 —— 这是修卡顿的关键）
- 随时「停止输出」
- 长输出自动折叠（超过 6 段收起，可展开）
- 自写 Markdown 渲染（标题 / 列表 / 引用 / 代码块 / 粗体 / 行内代码），不用系统 `AttributedString` 的 inlineOnly 模式（那个会把段落和代码块挤成一行）
- 专家对话顶部有固定身份横幅，和普通对话区分
- **草稿态**：点专家不会立刻建会话，发第一条消息才落库（修掉了"点一下专家就多一个空对话"的老问题）

### 2.2 联网搜索（App 自带，与模型厂商无关）

这是整个 App 最重的自研模块（`WebSearchService.swift`，约 700 行）。

**搜索层 —— 4 源并行融合**：

- 搜狗 / 360 / 百度 / Bing RSS 四家**并行请求**，轮转合并去重
- 任何一家被反爬或抽风，其余自动顶上
- 同域名最多 2 条（避免一家百科占半壁江山，保证来源多样性）
- 噪音标题过滤（页脚备案号「京ICP证…」、纯域名标题等）
- 结果解析不依赖各家会改版的 CSS class，而是通用地提取"指向外部内容的 `<a>` 标题链接"，再按引擎过滤站内搜索页
- 可选填 Tavily / 博查 API Key 作为增强源；单源模式下也可手动指定引擎

**抓页层 —— 把网页变成模型能读的结构化文本**：

- **跳转页跟随**：搜狗 / 360 / 百度的结果是 `/link?m=…`，返回 284~416 字节的 `window.location.replace(真实地址)` 空壳，不是标准 302，`URLSession` 不跟随。App 会自己解出真实地址再抓一次（最多 2 跳）。**实测抓页成功率 0/6 → 4/4**
- 表格结构化提取：`<table>` → 每行一条，单元格用 `|` 分隔（**参数表不再串行错位**）
- 正文定位：滑窗打分跳过导航区，直接定位信息最密集的段落
- GBK / GB18030 页面混入非法字节时降级为 lossy 解码（否则整页丢失）
- 剥掉 script 后再提表格，并二次过滤 JS 伪表格（动态渲染站点的 JS 模板里会拼 `<td>`）
- 列表 / 标题 / 单元格各自成行，避免中文键值粘连

**执行层**：

- 一轮里模型发多个 `web_search` 时**并行执行**（收集类任务一次发 6 个也不排队）
- 工具调用轮次上限 8 → 16（收集类任务够做到"每个实体单独搜一次"）
- 每次搜索自动抓取 3 篇正文（默认从 2 提高），多给 3 个候选，抓失败自动换下一个
- 回答末尾附上本轮实际引用的来源链接（去重，最多 8 条）

### 2.3 文件、资料库与文档生成

**上传**（`FileImportService`）：多选，支持 PDF、Word(.docx)、Excel(.xlsx)、PPT(.pptx)、Pages/Numbers/Key、txt/md/markdown/csv/json/xml/html/log、图片；也能直接拍照或从相册选。

**解析**：

- PDF → PDFKit 取文本
- docx / pptx / xlsx → 自解 OOXML（自写 ZIP 读取，支持 stored 与 deflate）
- 纯文本 → UTF-8，失败回退 GB18030
- 图片 → Vision OCR（简繁英）

**生成**（`DocumentBuilder`）：纯 Swift 手写 OOXML 产出 docx / pptx / xlsx，PDF 走 `UIGraphicsPDFRenderer`，ZIP 用自写 `ZipWriter`（STORED）。不引第三方库。

**资料库**（`LibraryView`）：本地沙盒 `Documents/Files` 保存全部上传文件与 AI 生成文件。支持「全部 / 我上传的 / 生成的」筛选、文件名与内容搜索、收藏、预览、分享、删除、回到来源对话。

### 2.4 生图

火山方舟 Seedream（`doubao-seedream-4-0-20260415`）或智谱 CogView，按 Key 自动识别。支持基于对话里最近一张生成的图做编辑修改。

### 2.5 长期记忆

每 3 轮对话自动抽取一次（公司、项目、偏好等），注入后续 system prompt。可在身份设置里查看条目、单条删除、一键清空。只存本机。

### 2.6 身份、风格与外观

- **身份**：称呼 / 身份（创始人、总经理…）/ 公司 / 行业 / 当前最想解决的经营问题 → 注入每条对话
- **回复风格** 5 种：自动、正式、简洁、详细、友好（切换后立即全局生效）
- **外观主题** 6 套：海蓝、石墨、翡翠、罗兰、珊瑚、鎏金

### 2.7 多会话管理

新建（先选顾问）、按标题搜索、长按重命名、滑动删除、侧栏按最后活动时间倒序、打开会话自动滚到最新。左下角液态玻璃悬浮按钮新建对话（Xcode 16.2 没有 iOS 26 的 `.glassEffect()`，用 `ultraThinMaterial` + 渐变描边 + 双层阴影模拟）。

### 2.8 备份与迁移（加密）

- **算法**：AES-256-GCM；密钥由 PBKDF2-SHA256 派生（12 万轮，随机盐用 `SecRandomCopyBytes`）
- **文件格式**：`BOSSAI01`（8 字节 magic）+ salt(16) + nonce(12) + 密文 + tag(16)
- **内容**：全部对话与图片、资料库文件、长期记忆、身份设置、API 密钥、偏好与预算
- **导入是合并式**：与本地同一条的数据跳过，不覆盖现有对话；导入后自动刷新 Key 让 App 立即生效
- 导出文件可直接存到「文件」App，换设备时传过去用同一密码导入

### 2.9 成本与预算

月度预算上限（元，0 = 不限），按 token 估算累计，App 内显示"本月已用约…"，每月 1 日自动清零。超额后拦截新请求。预算与已用额度也进备份。

### 2.10 设置与隐藏入口

**设置页**：粘贴 Key 后自动识别服务商（探测 `/models`）、「连接自检」显示两个 Key 实际落到哪家厂商、「恢复内置 Key」、自定义模型 ID 覆盖、搜索引擎选择、每次抓取正文篇数、预算上限。

**隐藏设置**：连点侧栏「Boss AI」标题 5 次（间隔 < 0.8s）+ 密码进入。

## 六、已知问题与限制（照实列）

**1.（已修复，待编译验证）跳转页抓取失败**  
360 / 搜狗 / 百度返回的结果链接是 `so.com/link?m=…` 这类跳转链接，访问后返回的是 **284~416 字节的 JS 跳转页**（`window.location.replace("…")` + `<meta http-equiv="refresh">`），不是标准 HTTP 302，`URLSession` 不会跟随。  
后果：抓正文拿到的是空壳 → 修复前实测**抓页成功率 0/6**，模型只能看到搜索摘要，参数类信息就全靠记忆补 —— 这是"资料收集不准"最致命的一环。  
修复：`fetchPageText` 里若拿到空壳，用正则解出 `location.replace` / `location.href` / meta refresh 的目标地址再抓一次（最多 2 跳，且只对空壳页做，不给正常页面增加开销）。**修复后实测 4/4 成功，每篇 1783~2817 字符。**

**2.（已修复，待编译）搜索引擎时好时坏 + 融合第二轮补不回（Q01）**  
同一查询在不同时刻，搜狗 / 百度 / Bing 都可能返回 0 条，只有 360 相对稳定 —— 这正是必须做多源融合的原因。  
曾有两个叠加的坑把单源结果砍到只剩 2 条：① 同域名限流 —— 360 的结果 url 全是 `so.com/link?m=…` 跳转链接，host 全是 `so.com`，限流直接一刀切；② 第二轮"放宽补齐"里 `seen` 在第一轮域名限流**之前**就写入，被跳过的条目 key 已进 `seen`，第二轮 `seen.insert` 恒为 false，补不回来。  
修复：两阶段融合 + `mergedKeys` 只在**确认收录**时写入（被限流跳过的条目不写）。**实测融合条数 2 → 6。** 注意：限流按"跳转链接的 host"判断仍不理想，理想做法是解跳转后用真实域名去重——留作后续优化（N 系列）。

**3.（已修复，待编译）纯域名标题 + 日期识别失效（Q02）**  
360 结果里会出现 `news.china.com` 这类把域名当标题的条目，和真实标题指向同一页，浪费抓取预算。  
修复时发现根因更隐蔽：纯域名正则全是 `(?:...)` 非捕获组，而 `firstMatch()` 只取 group 1、要求 `numberOfRanges > 1` → **过滤其实一直没生效**；`findDate()` 的 6 条日期正则也都没括号，日期识别同样从未生效。已新增 `firstWholeMatch()`（返回整个匹配）给这类"判断是否存在"的正则用，两处一并修复并验证通过。

**4. 动态渲染站点抓不到正文**  
汽车之家配置页、部分今日头条页面的内容由 JS 渲染，静态 HTML 里没有数据。这是移动 App 抓取的固有限制，只能靠多源多页覆盖。

**5. 参数页现代布局不用 `<table>`**  
ZOL / PConline / 京东都用 div + span 布局，表格结构化提取对它们无效，只能靠正文定位 + 单元格分隔符改善。

**6. 本轮改动尚未云端编译验证**  
搜索管线的一批修复已完成并通过静态自检 + 离线实测：跳转页跟随、表格提取、正文定位、lossy 解码、JS 伪表格过滤、并行搜索、噪音过滤、两阶段融合（Q01）、纯域名与日期正则（Q02）、草稿机制统一。**但还没推送到 GitHub Actions 编译，缺 GH_TOKEN。**

**7. SideStore 续签**  
免费证书 7 天有效期，需要 App 保持后台刷新或配快捷指令自动化。详见 `docs/SideStore中文安装与排障指南.md`。
