## 真实失败

`outputs/native-copy-rollout-20261117/live-3/`：完整长上下文规划 HTTP200，16字段/464字，六能力、公司、电话均有，内部核对记录没有进入定稿。但是模型把 `image_plan.intent` 写成 `poster`，把 `visual_style` 写成长段自然语言；实际执行只接受已定义枚举。图片入口在付费生成前422拒绝。此次真实图片0张，规划成本暂记0.036162元；临时账号、任务已清，策略恢复。含“（不构成节能承诺）”的商业文案仍需逐项审美/语义验收，不能以机器内容门禁代替完整成品验收。

## 根因与方案

模型已收到含枚举的 tools schema，却仍返回非法值。API没有在交付旧手机前执行相同计划校验，直到图片服务才发现，已经错过现有的一次有界修参机会。此前只用固定有效参数的测试没覆盖这个真实失败。

沿用已有 `shared/image-workflow.compile` 校验器作为双方共同契约，在 API `finalizeImageCalls` 增加计划检查；`poster-reference-readiness.assertNativePlanCalls` 区分计划枚举与素材数错误。扩展现有 `image-tool-repair` 的可修原因、字段白名单和明确枚举诊断。只允许一次修复，重检失败不把错误工具参数释放给手机，不发出图片调用。完整配色、摄影、构图、正文仍保留在原 prompt/design_brief，枚举只是执行分类，禁止把任意风格固定成蓝金或同一模板。

规划校验的 `owned-slot` 仅验证已选择图片数量与元数据索引；不代表图片已上传、不证明账号归属。图片服务仍负责真实素材查验；不会借用其他账号图片或凭空补图。

- [Ajv 官方校验规范](https://ajv.js.org/faq.html)、[修改数据的边界](https://ajv.js.org/guide/modifying-data.html)：借鉴统一校验、诊断后修复，而不是静默删字段/强制改值。Ajv 为 MIT / NodeJS 方案；本轮复用项目现有校验器，未新增 Ajv 或其他依赖，也不把社区建议当作实际画质证据。
