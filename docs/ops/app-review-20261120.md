## 一、官方文档给到的硬约束与硬能力

### 1.1 DeepSeek（对话/规划这一层）

来源：DeepSeek 官方 API 文档与模型页（deepseek-flash = DeepSeek-V4.1-Flash-1017）。

| 项 | 数值 | 对我们的含义 |
|---|---|---|
| 上下文 / 最大输出 | 1M / 384K | 足够放下整段对话 + 参考图，不需要截断 |
| 视觉 | 原生多模态，支持图片 | 能读参考图，但**不是 OCR** |
| 图片计费换算 | 按尺寸折 token，**总像素约压到 800×800 等量**，单张最多 384 token | **这是关键**：1625×1920 的海报喂进去，实际只按 ~800×800 的像素量处理，8–12px 的小字基本糊掉 |
| 单图限制 | base64/URL ≤32MB，单请求内联 ≤48MB，最长边 8192 | 我们能传大图，但传大图不会提高识别精度 |
| 峰谷价 | 输入未命中 1/2 元、输出 4/8 元（每百万 token，谷/峰） | 高峰＝工作日 9–12、14–18；批量任务挪到夜间可省一半 |

**结论**：让对话模型「照着参考图把文字抄下来」这条路，在官方计费/缩放规则下**从原理上就不成立**。今天实测的 `PGM接口→PoE/PWM`、`多防区→多协议`，以及更早的 `400-7758-119→183-3628-2668`，都是这个原因，不是模型笨。

### 1.2 Seedream 5.5（生图这一层）

来源：火山方舟《Doubao Seedream 5.5 教程》（更新 2026-11-19）与官方发布博客。

| 能力 | 官方描述 | 我们是否在用 |
|---|---|---|
| Model ID | `doubao-seedream-5-5-261028` | ✅ 线上就是这个 |
| 文生图 / 单图生图 / 多参考图 | 最多 10 张参考图 | ✅ |
| **图层拆分** | 1 张底图 + 最多 99 图层，`layer_decomposition_options.max_images` 2–100 | ⚠️ 代码支持，但只在模型主动要求时触发 |
| **富文本 OCR** | `text_recognition`：返回每行文字、`bounding_box.absolute/normalized`、字体、颜色、粗体/斜体/下划线/阴影/半透明 | ❌ **从未主动调用** |
| 多轮编辑一致性 | 非编辑区域**像素级保持**，官方演示 100 轮；建议 `background=opaque` | ⚠️ 我们的「再改一次」是整图重绘，没用这个 |
| 原生 RGBA | 文生图/图生图都能出透明素材 | ❌ 未用（Logo 合成可以用） |
| 分辨率 | 档位 1K/1.5K/2K，或显式 `宽x高`，总像素 [921600, 4624220]，宽高比 [1/16,16] | ✅ 用档位 |
| 文字崩坏率 | 严重 0.4%、轻微 1.7%（官方评测） | 作为验收基线 |
| 定价（官方） | flash 0.12、lite 0.22、4.5 0.25、4.0 0.20 元/张；5.5 按像素档，>2.61M 约 0.30 | 我们实测供应商成本 0.23（小图）/0.28（4.2M px） |

**结论**：我们买的是 5.5，但只用了它「画图」的一半能力。**图层拆分 + 富文本 OCR + 像素级多轮编辑这三项，恰好对应我们最痛的三件事**（原文提取、改字、局部修改），目前一项都没接。

## 二、同质产品怎么做（社区共识）

来源：即梦官方教程与多篇商业海报实战复盘、AI 海报技术流程分析。

三条被反复验证的做法：

1. **分层生产**：背景层（干净、无字、预留文字区）／主体层（参考图锁形）／文字层（排版引擎出）。理由是扩散模型是「全局控制」，同时要求背景好看+主体精准+文字正确，概率极低。
2. **正文小字一律不让模型画**：模型只允许尝试 2–3 个大标题字；正文、参数、电话、地址全部后期排版。
3. **混合方案是 2026 主流**：排版引擎保证「字对」，扩散模型保证「好看」，OCR 做质检员；品牌信息（Logo/公司名/电话）永远不交给模型。

对照我们：第 1 条我们有了（native-copy），第 2 条**没做到**（文案 <250 字就走模型画字），第 3 条**只做了一半**（有覆盖校验，但没有 OCR 质检、没有把官方 OCR 当作原文来源）。

## 三、现状扫描：我们缺什么

### 3.1 已具备（不要重复造）

- `native-copy-*` 五个模块：转写、字形排版、文字覆盖率校验、图层配准、预算控制
- `poster-reformat`：显式「整图重排」意图识别与画布重算
- `commercial-composer`：文案 ≥250 字时走程序叠字
- 意图层（11-20 新增）：比例锁定、热线补齐、占位清理
- 品牌记忆（11-20 新增，待部署）：公司名/热线/Logo 长期记忆

### 3.2 五个真实缺口（按严重度）

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| 1 | 参考图原文靠对话模型「看」，而它拿到的图被压到 ~800×800 | 官方图片计费规则 | 术语/号码错（PGM→PoE、多防区→多协议、400 号码画错） |
| 2 | 文案不足 250 字时，文字交给模型画 | `commercial-composer.js` 的 `Math.max(250,…)` | 短文案海报必错字（11-20 实测 3 次里 2 次有问题） |
| 3 | 「再改一次」是整图重绘，不是局部编辑 | 12:53→12:54 两次出图尺寸全变 | 上一轮满意的地方被重画、主体变形 |
| 4 | 比例靠模型临场决定 | 同一需求出现 0.845/0.75/4.1:1/0.5625 | 客户要竖版却出横条 |
| 5 | 无生成后质检、失败话术不实 | 12:55/12:59「图片没有产出」但台账无调用 | 客户觉得被敷衍 |

### 3.3 成本现状

- 单张供应商成本：小图 0.23 元、4.2M px 0.28 元、含参考图 0.33 元（10-20 台账实测）
- 一次「不满意→重生成」平均 2.4 张（今天 5 次出图/2 轮需求）
- 无「草稿/定稿」分层，所有请求都按 2K 出

## 四、优化方案（按优先级）

> 每条都写清：改动范围、验证标准、预计影响、成本变化。**全部本地实施，验收通过才发。**

### P0-1 参考图原文提取改用官方富文本 OCR

- **做法**：在 bf-image 生成前加一步 preflight——把用户上传的海报丢给 Seedream 5.5 `layer_decomposition:true, text_recognition:true, max_images:2`，拿回 `text_recognition`（逐行文字+坐标+样式）作为**唯一可信原文**，替换对话模型转写的文案。
- **依据**：官方文档明确该接口返回「文字内容、逐行位置、近似样式」；社区混合方案的「引擎负责语义正确」。
- **改动范围**：`bf-image` 新增 `extract-reference-text.js`；`bf-api` 在 image 工具调用前调用并把结果塞进 `structured.text`。不动 App。
- **验证**：取 20 张真实客户海报（含 11-20 这张产品页），逐字比对，字符准确率 ≥99%、号码 100% 正确；对比现行方案基线。
- **预计影响**：转录类错字基本清零；每张多一次调用，成本 +0.12~0.22 元。
- **降本替代**：只在「参考图文字量 >80 字」或「用户要求按图重绘」时触发，其余走轻量规则。

### P0-2 品牌信息强制走排版层，禁止模型绘制

- **做法**：Logo、公司全称、400 热线、地址一律不进 prompt，改由服务端在底图上叠字/贴图（幂等、可回读校验）；生成后 OCR 回读一次，不匹配就重排版而非重生成。
- **依据**：社区共识「品牌关键信息一律用设计软件严格还原」；官方 5.5 支持原生 RGBA（Logo 可直接贴合）。
- **改动范围**：`bf-image` 的合成阶段；`bf-api` 的品牌槽位填充。
- **验证**：50 次生成，电话号码错字 0、占位文字 0、Logo 缺失 0。
- **预计影响**：品牌类投诉归零；无额外成本（省掉重生成）。

### P0-3 短文案也走叠字，取消 250 字门槛的「放行」

- **做法**：文案长度不足时不再让模型画字——要么由模板补足（标题/副标题/联系条），要么强制 `text_mode=overlay` 走排版。
- **依据**：官方 OCR 能力 + 社区「正文小字一律后期加」。
- **验证**：短文案海报 30 张，错字率 ≤1%（对照现在约 30%）。
- **预计影响**：短文案海报从「抽卡」变成「稳定可用」。

### P1-1「再改一次」改走 5.5 多轮编辑

- **做法**：当用户基于上一张提修改时，用上轮结果作 `image` 输入、`background=opaque`、prompt 写明「只改 X，其余保持不变」。
- **依据**：官方「非编辑区域像素级保持，支持 100 轮」。
- **验证**：改字/改色后，未编辑区域 SSIM ≥0.98；主体结构不变。
- **预计影响**：多轮返工不再越改越差；成本与现在持平（同样的单次调用）。

### P1-2 比例白名单 + 意图锁定（已部分上线）

- **做法**：服务端只接受 1:1 / 4:5 / 3:4 / 2:3 / 9:16 / 16:9 / 4:3 七档；意图层已能锁定方向，再补「显式比例优先」。
- **验证**：100 次请求，比例符合率 100%，不出现 4.1:1 这类异常画布。

### P1-3 生成后 OCR 质检 + 一次自动修

- **做法**：生成后用 `text_recognition` 回读成品，与期望文案逐条比对；不符则触发一次「只修文字」的局部编辑，仍不符则如实告知并给出差异清单（不再说「没有产出」）。
- **验证**：质检覆盖率 100%；误报率 <5%；失败话术与实际台账一致率 100%。

### P2-1 成本分层（草稿/定稿）

- **做法**：首轮用 1K/1.5K 出草稿，用户确认后再 2K 定稿；预览走 flash 档。
- **依据**：官方 5.5 支持 1K/1.5K/2K 档位；flash 0.12 vs lite 0.22 vs 5.5 ~0.30。
- **预计影响**：单次需求总成本降 30–40%（按今天「平均 2.4 张」估算，从 0.66 元降到 0.40 元左右）。

### P2-2 失败不计费 + 幂等（已有，补验收）

- 已有同 requestId 幂等（实测金额零增量）；补「上游失败不计费」的对账用例。

1. 所有改动在 `worktree/` 本地完成，配套单测 + 真实样例回归（20 张真实海报）。
