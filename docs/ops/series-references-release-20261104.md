## 代码证据与兼容方式

旧 `image_series` 工具 schema 没有 structured，不能只检查它有没有这个字段再启用。其实际执行器会接受字典参数，`startSeries` 已支持透传 structured。因此服务端只给现有 image_series 增加可选 metadata，保留工具名、prompt、count 和返回 items 格式，没有新增客户端需要执行的工具。

- `shared/sync-identifiers` 提取现有同步 key 算法，UUID仍由原协议转为大写，不改变同步记录身份。
- `image-reference-store` 通过该账号的 file 同步记录解析历史 UUID，校验原图 asset 的账号、类型、摘要和 ready 状态，保留角色与顺序。
- `bf-api/image-series-reference-guidance` 只认可配对 recall_history 的工具返回编号，不把用户随便打的 UUID 当检索凭据。读取并复核账号原图后才给模型候选，强化现有组图 schema，并将选中的 library_refs 转为 structured.image_references。非法、未发放或冲突的引用在返回手机前拒绝。角色放在新契约内部，不留会触发旧解码器 source_indexes 校验的顶层 reference_roles。
- 没有历史素材、没有组图工具时不读取素材库，不注入额外指令；普通文生组图保留原流程。历史库尚未同步时不能只拿文字描述伪称已带原图。
- `/series/start` 在供应商调用及额度预留之前校验原图，只保存不含 URL/图片像素的 manifest。来源选择和角色形成指纹，同 requestId 换素材拒绝；原请求重放复用任务。原始图像直接塞入 start 而没有可恢复资产时明确拒绝，不再静默丢图。
- 子图在 claim 后重新按账号检查 manifest，再签短期链接，按顺序把所有原图和角色实际交给模型。素材删除或被替换时失败关闭，不回落无图生图，也不因缺图扣费。
- 已寄出客户端使用的 `/series/retry` 现在能找到 v2 持久任务，复用同一子图执行器补失败项；已成功的项不再生成。取消和跨账号访问仍拒绝。
- 子图计价与最坏额度预留纳入实际输入图数，避免 Pro 多图附加费用漏算。start、同步组图和失败项重试共用最坏单价函数；重试在启动供应商前校验整批剩余额度，不跑到一半再发现不够。倍率和路由配置没有改变。

2. 使用缺少 structured 的旧式工具 schema 发起真实模型规划，返回两项有序 structured 引用。
3. 原请求 start 重放返回同任务；交换素材顺序409；另一账号引用该素材422、访问任务403；上述操作没有图片供应商调用。

5. 产物同时出现咖啡场景和消防车，证实两份输入实际参与本次结果。重放该成功子图及旧 retry 接口后，图片调用数仍为1；取消未执行的第二张，不浪费第二次生成。

**质量边界**：这是一项来源透传测试，不是商业海报、人物保真或全部视觉质量验收。前置模型在未看到画面的情况下，曾将第二份通用素材脑补为“人物”；Seedream看到实图后实际使用了消防车。不能把该样例用于宣称前置素材理解已完善。下一步应完善检索→描述/预览→素材角色确认，不能继续仅把编号包装成“看过原图”。此前含乱码的高密度参展海报仍不合格。

## 回滚必须保住新任务语义

不能直接把图片函数恢复成旧 ZIP：即使先回退 API，旧 App 仍可能缓存新引用参数或已有新 taskId；旧图片代码会忽略 manifest，从而再次丢图。

已准备 `rollback-compatible-functions` 和 `bf-image-rollback-compatible.zip`：保留上线前全部实现，只在 start、单图入口和 step 明确拒绝新引用任务，返回可读维护提示，避免静默无图生成。候选通过 Node 语法与 ZIP 门禁，只有 index.js 与旧包不同。需要回滚时先备份当时最新线上补丁，先回退 API，再使用这个**带兼容守卫**的图片回滚目录，不使用裸旧包；新引用任务暂停到修复后继续，旧文生任务保持原行为。不要删除/重写客户任务或跨账号补素材。
