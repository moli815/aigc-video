## 3. 源码根因：按影响排序

### P0-A：把“参考真实产品”混成“重新设计参考图”

`cloudfunctions/bf-image/index.js:1231` 的 REFERENCE_CONSTRAINTS 要求重新设计整张作品、不保留现成构图；`:1413` 对带图 reference 直接拼接。`multiImageContract` 对reference也规定重构版式。

这对“把旧海报换成动漫风”合理；对“用这个真实大屏做海报/放进指挥中心”就过宽：**可以重做外部海报，但大屏这个产品资产应另有不可重绘的保护义务。** 当前缺少这个分层语义，不应简单把所有reference改成edit，或反过来全部强制原样不动。

### P0-B：准确排字分支主动排除真实UI，创作意图传不到完整作品

- `bf-api/commercial-image-guidance.js:19` 要求 artwork_prompt 不描述数据或界面；`image-tool-schema.js:17` 对商业image_generate把独立物理场景素材简报设为必填。
- `bf-image/commercial-artwork.js` 进一步禁止绘制看板界面。`index.js:1392` 命中composition后用该素材简报替换原完整视觉prompt。
- `index.js:1240/1420` 的无字约束禁止文字和数字；若保护对象是本来就含大量字和数字的UI，会与保留要求冲突。
- `commercial-poster-scene.js:87` 将主要配图高度限制为画布约17%/18%/28%，另有宽度上限、裁切/遮罩。schema只提供3个style_id、6个layout_id。

因此，**上游即使是Pro，也经常只负责无字小素材，并没有获准设计完整海报**。这能解释“普通AI配图+文字”“风格单一”。准确字体组件本身没有错，错误在于把一种止乱码的实施路径变成通用创作底座。

### P0-C：Logo精确合成依赖旧手机，服务端看不到完整最终结果

- `BossAI/Services/PreservedAssetWorkflow.swift:45` 仅在edit且有preserve_assets、有效两图和合法box时启用。Agent漏参数就可能退回模型重画，品牌变成“像但不是”。
- `ImageToolArguments.swift:31` 对精确Logo要求source=both或至少两张library_refs；两个本轮上传附件不能直接冒充both。
- 精确保留路径会先移除Logo参考，**只把需清理的底图送模型，再由手机抠图和合成**。此时账本inputImages=1是正常现象，不能统一视为丢Logo。
- `BrandPlacementPlanner.swift` 按短边16%、边距5.5%和方位吸附落位；不是任意精确box，也没有全图OCR/主体避让验收。模型估算小框，手机最终贴到另一块，仍可能压字。
- `BrandAssetCutout.swift` 已有纯色去底、Vision主体分割及失败分支；不能说“已经有真正通用Logo分割”，复杂海报里的小Logo/文字/镂空结构仍需实测。
- `bf-api/index.js:252` 的一般工具指导“不使用both”与后续品牌特例“使用both”并存。即便后注入特例，也是在增加模型解释负担，应由一份来源决策契约消除冲突。

这部分**不能只改bf-image中的一句prompt保证修好**：某些Logo根本没走到图片服务器，最终合成又在手机。可通过兼容旧协议的服务端独立合成路线接管，但要先证明能绕开本地重复贴图，见第5节。

### P0-D：记住了“必须放Logo”，没有记住“这个Logo是哪份资产”

`ImageMemory.swift` 从文件名+textContent做词项召回，最多返回4张；`ContextRecall.swift` 是中文相邻词片段/英文词匹配，不是语义视觉检索。需要Agent发起recall_history，拿到真实ID，再选原件。`include_images` 才带预览，客户端最多预览两张。

`MemoryService.swift` 注入相关记忆最多12条+4条补充，受5500字符预算限制；不是自动将所有品牌资产强制绑定到每次任务。`confirmed-image-context.js` 是同会话原文保护，不是完整跨会话多模态记忆：云端恢复有近期100条、锚点和会话归属限制。`context-compaction.js` 明确不保存旧图片像素。

因此，文字摘要、图片说明、可访问原图是三个不同对象。当前没有可靠串成“公司身份 → 当前有效Logo → 用户长期规则 → 本次必须使用的资产”。单加更长上下文或一个memory skill解决不了这个断点。

### P1-E：前置看图细节不足，不能误判为Seedream只收到768图

`HostedAccount.swift:773` 会应用云端768/0.65；`ChatViewModel.swift:709` 的普通附件预览使用ImageCompressor。密集大屏的小字和小Logo更难定位。

但 `ChatViewModel.swift:297` 获取作图参考时读取原文件，`ImageService.swift:374` 上传参考原字节并签发URL。**压缩主要影响前置识别/规划，不等于实际Seedream参考图必然被压到768。** 老文件已丢失的细节也无法靠服务器把数字调大恢复。

### P1-F：审稿不等于事实/素材验收，思考提示尚未全员启用

`commercial-copy-review.js:34` 只校对image_generate且文案≥420字符；明确“不看参考图”，失败返回原稿。它不验证Logo是否贴对、屏幕是否原图、完整prompt是否含错误电话。

另有可离线复现的缺口：validateReview把“原草稿+来源”一起当支持文本，**原稿本身已有的无依据电话号码，原样复述仍可通过校验**。本次直接调用源码函数验证返回true，没有付费模型调用。应以已确认来源验证联系方式，不能把草稿自证为事实。

当前图片设计指导已经有按用途思考/不默认极简等要求，但渲染分支落实不完整。对话行为V2尚关闭，不能宣称用户已经获得其改善；前置默认快速响应也不等于完成了真正独立的视觉审稿。不能通过要求展示长篇思考来代替结果验收。

## 5. 推荐的具体修复方案：服务端优先、保留模块边界

统一流水线：**任务理解 → 当前目标/长期事实合并 → 账号资产清单 → 设计计划 → Provider编译 → Pro生成 → 真实素材合成 → 内容/文字/视觉验收 → 归档与记账**。不是再在generate函数堆业务关键词。

### 第一步：质量与预览基线（配置候选，尚未改）

将IMAGE_ROUTING_MODE设为pro_only，保留官方Pro ID、IMAGE_FAST_MODE=0。这满足用户最新全Pro要求，不再混入Flash。先验证单图、编辑、图层与**已有服务端逐张组图编排**；不能把Pro不支持的原生sequential参数硬发出去，或关闭能力检查。

普通预览可先试长边1536、JPEG0.85作为候选；不是官方最佳值。现有聊天入口有2.6MB总请求限制、预览缓存且多图最多6张，因此不能全局直接拉到2K/最高质量。优先服务端按任务取已授权原图作精细识别；若调全局配置，必须跑多图体积/缓存/旧包回归，超限保留现有安全约束。Seedream参考资产继续原字节/私有URL路径，PNG Logo不经JPEG预览作最终素材。

### 第二步：独立“任务与资产计划”，消除互相冲突的prompt

在共享规划模块内部定义模式，而不是给旧工具新增必须参数：

| 模式 | 做什么 | 不可改变的内容 |
|---|---|---|
| 新商业广告 | Pro设计完整视觉；长文必要时用可执行图层精准排字 | 已确认品牌、事实和必需文案 |
| 实物/UI参考做海报 | 海报外部布局可重做，真实产品/UI作为保护资产 | Logo、界面内容、必要数据；不能概括成泛化蓝色大屏 |
| 场景融合 | Pro创作房间/人物/照明，原UI映射到指定屏幕，保留遮挡 | 产品身份与关键字段；不要求整幅场景原像素不变 |
| 添加/替换Logo | 识别空位或旧标识，必要时只调整局部，原Logo精确合成 | 正文、主要版式、Logo轮廓/字形/比例 |
| 明确风格重设计 | 放开外部构图、材质/插画媒介等 | 用户明确要求保留的品牌与业务信息 |

### 第三步：Pro负责创作，真实性资产有独立落位器
