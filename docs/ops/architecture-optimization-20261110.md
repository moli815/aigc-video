# App / 服务端 / 管理端架构优化与实施台账

日期：2026-11-10  
审计基线：`e73d5e2` + 当前工作区未提交改动  
范围：iOS App、`bf-api`、`bf-image`、`bf-jobs`、共享模块、管理端、员工端、专家目录、Seedream 接入、部署产物。  
边界：**先文档、后实施；服务端优先；不为了单项优化出 IPA；不覆盖现有 Swift、DSH、提醒功能和错误修复改动。生产部署仍需单独确认。**

## 1. 结论与执行原则

当前最需要修的不是“文件太长”，而是以下四类真实风险：

1. **付费边界不统一**：组图续步可绕过实时会员/额度检查，主图片开关没有覆盖 `bf-image`，账务新事件与旧事件走不同 CAS 路径。
2. **凭证与账号隔离存在客户端硬风险**：会员 token 可进入第三方 Provider 自检，全局身份可能跨账号注入；这些只能登记到下次构建，本轮不改 Swift。
3. **专家系统有三份模板和多套权限决策者**：后台新增专家可展示但旧 App 无法执行，可视化编辑会截断多行开场白，本地工作流与云端交付规则冲突。
4. **部署产物不等于审计源码**：shared 源码已部分收敛，但函数内生成副本会漂移；继续堆功能前必须建立干净构建和哈希门禁。

执行原则：

- 先阻断权限、额度、资金和错误凭据，再做体验优化。
- 保留已有 `ToolManifest`、`ImageUseCase`、`ArtifactRepository`、`SyncV2Engine`、shared 薄适配器，不做全仓重写。
- 每个修复必须有可注入故障的契约测试；“测试通过”与“真实质量通过”分开记录。
- 在线配置只用于已经有真实消费者的字段；不把“新增配置项”当作“能力已经实现”。
- 本轮产生的服务端候选不自动部署；必须备份、核对上传/下载产物后再单独确认生产发布。

## 2. 目标架构

```text
App UI
  → 不可变 ChatTurnContext（账号、会话、目录版本、工具策略、Provider）
  → ChatTurnRunner（轮次、取消、重试、最终状态）
  → EffectiveToolPolicy（本轮唯一权限快照）
  → ToolDispatcher → Image / Research / Document / Chart UseCase
  → ToolResult / ArtifactRepository / FriendlyError

托管服务端
  → 统一鉴权与能力门禁
  → 唯一模型/图片路由决策
  → Provider adapter
  → 幂等操作指纹 + 可恢复账务
  → 脱敏台账与统一错误目录

专家系统
  → 版本化 CatalogEnvelope
  → ExpertDefinition（展示、方法、能力、交付、知识绑定分离）
  → 每轮 EffectiveExpertContext
  → 本地内置快照仅作离线兜底，不与远程模板重复叠加
```

### 9.2 升级决策

- **不提前接 Seedream 5.5**：当前检索到的是发布消息与“API 本周上线”口径，官方价格页尚未列出可生产的 Model ID 和价格。等官方 API 文档、模型 ID、价格和账号开通均可核实后，再做隔离评估。
- 不为原生组图立即切 Lite：现有云端编排支持独立幂等、逐张记账和部分成功，原生组图只有在质量一致性明显收益且失败/计费语义验收后才考虑。
- **成熟方案复用边界**：GitHub MCP/ComfyUI 项目可借鉴自动转存、参数能力矩阵和任务编排，不引入另一套运行时到生产 App；第三方聚合通道不替换官方主链路。
- **真正需要客户端的新能力**：框选/箭头/坐标编辑、图层选择与二次排版、4K 下载与预览，统一放后续构建，不在本轮假称已上线。
