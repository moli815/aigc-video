# BossAI 全链路优化执行方案

> 执行模型：DS4.1 Flash 1017
>
> 当前策略：继续全量使用 Pro。全部问题修复并验收通过后，才允许切换 auto。
>
> 本文档只指导代码修改，本轮不要直接修改云端生产代码。

## 一、目标与原则

本轮解决四类问题：

1. 图片编辑不忠实：裁切、构图漂移、人物脸部变形、背景被重绘。
2. 名片不稳定：重复渲染、比例错误、文字乱码、文字溢出。
3. 用户体感慢：上传、规划、生图、校验、重试、结果解释链路过长。
4. 云端稳定性：鉴权异常、超时不一致、管理端同步操作风险。

原则：

- 先修 P0，再修 P1，最后做体验优化。
- 不用继续追加提示词掩盖架构问题。
- 本轮不切换模型路由，不把问题归因于模型档位。
- 每阶段完成后运行构建、静态检查和回归测试。
- 不提交密钥、Token、完整请求头、环境变量或用户原图内容。

## 二、涉及文件

客户端：Services/ImageTaskPlanner.swift、Services/ImageService.swift、Services/HostedAccount.swift、Services/PosterLayout.swift、Services/PosterComposer.swift、ViewModels/ChatViewModel+Streaming.swift、Services/BoundedHTTPClient.swift、Config/AppConfig.swift。

云函数：bf-image/index.js、bf-api/index.js 及运行时环境变量。

管理端：admin-service、bf-admin 静态应用及其调用代码。

## 三、P0：先修稳定性和架构错误

### 3.1 修复 bf-api 鉴权空密钥异常

线上曾出现 TypeError: Cannot read properties of null (reading tokenSecret)。原因是鉴权密钥没有成功加载时，verifyToken 仍直接访问空对象。

要求：

1. verifyToken 在 HMAC 前检查 token、secret 和两段格式。
2. 无 Token 或无效 Token 返回 401。
3. 密钥未加载或数据库不可用返回 503。
4. requireMember、requireStaff 及所有鉴权入口不得产生未捕获异常。
5. 日志只记录 requestId、错误类型和阶段，不记录 Token 或密钥。

验收：无 Authorization 稳定返回 401；随机 Token 稳定返回 401；模拟密钥加载失败返回 503；日志不再出现 tokenSecret 空对象 TypeError。

### 3.2 统一超时、取消和错误码

线上存在客户端或网关取消后云函数继续执行的问题。建议层级如下：

| 层级 | 普通对话 | Pro 图片编辑 |
|---|---:|---:|
| 上游模型 | 90 秒 | 260 秒 |
| 云函数内部 | 120 秒 | 280 秒 |
| 网关/服务端 | 150 秒 | 300 秒 |
| 客户端 | 165 秒 | 315 秒 |

要求：

1. 客户端取消后服务端停止后续视觉验证和自动重试。
2. 每个阶段检查请求是否已取消。
3. 统一错误码：UPSTREAM_TIMEOUT、CLIENT_CANCELLED、GATEWAY_TIMEOUT。
4. 日志记录上传、规划、生图、下载、相似度检测、视觉验证、排版耗时。
5. 不要只提高超时来掩盖网关取消问题。

### 3.3 修复重试丢失任务参数

文件：ViewModels/ChatViewModel+Streaming.swift。

视觉验证或编辑相似度失败后的重试必须继承首轮完整上下文。目前可能丢失 taskKind、qualityTier、requestedCount、aspectRatio、renderIntent 和 structured。

建议定义不可变的 ImageRequestContext，首轮、相似度重试、视觉验证重试都复用它，只允许追加重试说明。

验收：首轮 Pro 编辑重试仍是 Pro 编辑；名片重试仍是名片任务；组图数量不丢失；日志中首轮与重试的 taskKind、qualityTier、aspectRatio 一致。

### 3.4 取消名片双重渲染

当前 HostedAccount.renderPoster 已调用 PosterComposer.compose，回到 ChatViewModel+Streaming.swift 后又调用 PosterLayout.render，可能造成文字重复、背景变暗、布局二次改变。

只保留一个最终合成入口：

AI 生成无文字底图 → PosterComposer 程序排版 → 返回最终名片 → ChatViewModel 直接展示和保存。

要求：

1. renderPoster 返回最终图片后不得再次调用 PosterLayout.render。
2. 名片和通用海报使用不同任务分支。
3. 名片不能套用通用竖版海报的底部暗色遮罩。
4. 增加 render_stage_count 日志；名片必须为 1。

验收：文字只出现一次；背景不被二次变暗；横版名片不被套成竖版海报。

## 四、P1：图片编辑质量

### 4.1 编辑任务保持原图比例

文件：ImageTaskPlanner.swift、ImageService.swift、bf-image/index.js。

要求：

1. 编辑任务读取原图真实宽高比，不能默认回落到 1:1。
2. allowCrop 默认必须为 false。
3. 服务端记录原图比例、请求比例和是否允许裁切。
4. 请求比例与原图不一致且未明确允许裁切时，服务端强制使用原图比例。
5. “不要裁切”不能只写在提示词里，必须落实到尺寸和任务参数。

### 4.2 拆分三类图片任务

不能把所有改图都归为同一种 edit。

风格转换：只改变色彩、光影、风格；不改变人物身份、人物数量、主体位置和画布比例，不新增对象。

局部修改：需要 mask 或明确区域；未选区域保持；默认保护人物脸部和文字区域。

人物合成：需要独立人物参考图、位置、大小、朝向和遮挡关系；向用户提示公众人物脸部不能保证完全一致。

客户端 taskKind、服务端日志和 UI 文案必须能区分三类任务。

### 4.3 改进相似度和重试

全图像素相似度只能判断整体是否相似，不能判断脸部、手部和文字是否正确。

要求：

1. 至少记录全图相似度、主体区域相似度（可实现时）、比例是否一致、尺寸是否一致。
2. 重试最多一次。
3. 重试必须保持同一模型、任务类型、比例和参考图。
4. 用户明确要求大幅换风格时，不要仅因相似度下降就误判失败。

## 五、P1：名片和海报

### 5.1 AI 只生成底图，程序绘制精确文字

名片、证书、海报、宣传单统一采用：AI 生成背景/装饰 → 程序绘制真实文字和结构元素 → 检查越界、重叠、截断 → 输出最终图片。

电话、邮箱、地址、姓名、职位、公司名、二维码和精确数字不能交给图片模型生成。

### 5.2 新增独立 BusinessCardRenderer

职责：

1. 固定名片比例和安全边距。
2. 读取真实业务字段。
3. 绘制 Logo、姓名、职位、电话、邮箱、地址。
4. 检查 bounding box、重叠、越界和截断。
5. 超出时自动调整字号、行距或布局。
6. 无法布局时返回失败，不展示坏图。

名片和海报不得共用默认比例、底部遮罩和布局规则。

## 六、P1：速度优化（暂时保持全量 Pro）

### 6.1 减少额外模型调用

普通风格转换、草图预览、非名片/证书/正式印刷物默认关闭视觉验证。名片、证书、正式海报和用户主动要求质量检查时可以保留。

验证失败时不要默认整图重生成，优先提示用户选择重试或局部修改。

### 6.2 上传并发和缓存

文件：Services/ImageService.swift。

要求：多张参考图并发上传；图片内容哈希不变时复用已上传 URL；上传凭证支持批量时使用批量接口；记录上传独立耗时；压缩不能明显破坏人物脸部和名片文字。

### 6.3 展示真实阶段进度

建议阶段：正在准备参考图、正在提交 Pro 生成、正在下载生成结果、正在进行质量检查、正在完成排版。

阶段必须支持成功、失败和取消，不要只显示固定的“正在生成”。

## 七、P1：管理端

### 7.1 列表分页

admin-service 列表接口必须强制分页、限制单页最大数量、禁止默认全量读取，并返回总数或是否有下一页。

### 7.2 导出异步化

改为：创建导出任务 → 后台生成文件 → 保存任务状态 → 管理端轮询 → 返回临时下载地址。不要让 HTTP 请求同步等待大数据导出。

### 7.3 权限去硬编码

管理员身份、角色和状态全部从数据库读取；删除硬编码白名单和固定初始化身份；seed/初始化入口必须一次性、可关闭、可审计；删除、导出、权限变更都要记录审计日志。

当前 admin-service 超时约 3 秒，不能靠单纯提高超时解决；列表靠分页，导出改异步，删除限制批量。

## 八、P2：代码质量

1. ExpertCore/ReliabilityCore.swift 中的 try! NSRegularExpression 改为安全初始化，配置异常不能导致 App 崩溃。
2. BoundedHTTPClient.swift 统一 request timeout、resource timeout、取消、重试、request ID 和错误码映射。
3. 日志统一包含 requestId、taskId、taskKind、qualityTier、aspectRatio、阶段耗时、是否重试、最终错误码。
4. 日志禁止记录 Token、API Key、完整 Authorization、完整请求头、完整图片内容和完整用户联系方式。

## 九、严格执行顺序

阶段 1：修复鉴权空密钥、统一取消/超时、修复重试参数丢失、增加阶段耗时日志。

阶段 2：取消名片双重渲染，拆分名片/海报，AI 只生成底图，程序绘制文字，加入布局检查。

阶段 3：保持原图比例，拆分三类任务，加入局部编辑能力；模型不支持 mask 时必须明确降级，不要假装实现了局部修改。

阶段 4：上传并发和缓存、减少非必要视觉验证、管理端分页、导出异步、权限去硬编码。

阶段 5：全部验收通过、观察线上日志后，才讨论切换 auto。此前严禁修改为 auto。

## 十、验收用例

图片编辑：

1. 横版原图换风格：比例不变、不裁切。
2. 竖版人物图换风格：脸部不明显变形。
3. 只改背景：主体和前景保留。
4. 增加人物：使用明确的人物合成提示和参考图。
5. 主动取消：云端停止后续重试和验证。

名片：

1. 横版名片保持横版。
2. 电话、邮箱、地址逐字正确。
3. 文字不重复、不溢出、不裁切。
4. 不出现“名片放在白纸上”的展示场景。
5. 排版失败时返回错误，不展示半成品。

性能与稳定性：

1. 日志能拆出上传、Pro 生成、下载、验证、排版耗时。
2. 普通单图不无条件触发视觉验证。
3. 重试最多一次且参数一致。
4. 客户端取消后云端不继续整条链路。
5. 无 Token、错误 Token、密钥不可用分别返回 401、401、503。

## 十一、完成标准

- P0 全部关闭。
- 名片只经过一次最终合成。
- 编辑任务不再默认改成 1:1。
- 图片重试不丢参数。
- 鉴权不再出现空对象 TypeError。
- 超时和取消行为一致且可观测。
- 名片文字由程序绘制并通过布局检查。
- 管理端导出不再同步阻塞。
- 全部验收用例通过。
- 线上观察期内没有新的 499、鉴权 TypeError 和重复渲染问题。

## 十二、给 DS4.1 Flash 的硬性约束

1. 本轮不要切换到 auto。
2. 不要修改模型配置来掩盖代码问题。
3. 不要无限重试。
4. 不要把名片精确文字交给图片模型。
5. 不要用提示词中的“不要裁切”替代比例和编辑策略控制。
6. 不要直接修改云端生产函数；先改代码、构建、测试，再由用户确认部署。
7. 每次修改后汇报：文件、问题、验证方式、剩余风险。
